# TripGo — лабораторная работа 1

HTTP-сервис на Go для создания, получения и завершения поездок. Данные хранятся
в PostgreSQL. Реализованы основная часть [лабораторной №1](https://github.com/course-go-autumn-2026/course/blob/main/homework/tasks/01-http-and-postgres/README.md)
и оба дополнительных задания: идемпотентность создания поездок и Docker-сборка.

## Требования

- Go 1.27.1 или новее.
- Git, Make и curl.
- Запущенный Docker; на macOS — Docker Desktop.
- Утилита курса [tripgoctl](https://github.com/course-go-autumn-2026/course-infra).

PostgreSQL поднимается через `tripgoctl`, отдельно устанавливать его не нужно.
Версии `goose` и `oapi-codegen` закреплены в `go.mod`: команды Makefile запускают
их через `go tool`. При первом запуске потребуется интернет для загрузки зависимостей.

## Запуск

В терминале выполните:

```sh
git clone --branch homework/01 https://github.com/KirillKrainov22/tripgo.git
cd tripgo
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
make migrate
make run
```

Если проект уже скачан, перейдите в его папку и пропустите `git clone` и `cd tripgo`.

`tripgoctl environment start` создаёт `.env` с адресом PostgreSQL. Копировать
`.env.example` в `.env` не нужно. `make run` сначала загружает `.env.example`,
затем `.env`, поэтому адрес БД берётся из запущенного окружения курса.
Эти файлы перекрывают одноимённые переменные терминала.

`make migrate` создаёт таблицы, `make run` запускает сервис на порту 8080.
Если обязательные настройки некорректны или БД недоступна, сервис не запустится.

В другом терминале проверьте:

```sh
curl -i http://localhost:8080/health
curl -i http://localhost:8080/ready
```

Оба запроса должны вернуть `200` и `{"status":"ok"}`.
Остановка сервиса — `Ctrl+C`. Остановка окружения — `tripgoctl environment stop`.

## API

| Метод и путь | Назначение |
|---|---|
| `POST /api/v1/trips` | Создать поездку |
| `GET /api/v1/trips/{tripId}` | Получить поездку по ID |
| `POST /api/v1/trips/{tripId}/finish` | Завершить поездку |
| `GET /health` | Проверить работу HTTP-сервера |
| `GET /ready` | Проверить доступность PostgreSQL |

Форматы запросов и ответов заданы в [OpenAPI-контракте](contracts/openapi/trip-service.openapi.yaml).
Успешные ответы возвращаются в JSON, ошибки операций с поездками — в
`application/problem+json` с полем `code`.

### Пример работы с поездкой

В отдельном терминале задайте данные и создайте поездку:

```sh
TRIP_DATA='{
  "user_id": "5cb72c04-7650-45c9-a79b-bcdba0631e0c",
  "driver_id": "8860b315-ec86-42eb-a17c-7c163d721ff5",
  "start_point": {"latitude": 59.9398, "longitude": 30.3146},
  "end_point": {"latitude": 59.9290, "longitude": 30.3626},
  "price": 1450
}'

curl -i -X POST http://localhost:8080/api/v1/trips \
  -H 'Content-Type: application/json' \
  --data "$TRIP_DATA"
```

Ожидается `201`: поездка в статусе `active` и заголовок `Location` с её адресом.
Скопируйте `id` из ответа и в том же терминале выполните:

```sh
TRIP_ID='<id из ответа>'
curl -i "http://localhost:8080/api/v1/trips/$TRIP_ID"
curl -i -X POST "http://localhost:8080/api/v1/trips/$TRIP_ID/finish"
curl -i -X POST "http://localhost:8080/api/v1/trips/$TRIP_ID/finish"
```

Получение вернёт `200`, первое завершение — `200` со статусом `completed`,
повторное завершение — `409 trip_completed`.

Пока поездка активна, создание ещё одной поездки этому водителю вернёт
`409 driver_busy`. Неверные данные дают `400 invalid_request`; в поле `detail`
указано, какое поле не прошло проверку и почему. Неизвестный ID —
`404 trip_not_found`, внутренняя ошибка — `500 internal_error`.
Для повторного прохождения примера сначала завершите активную поездку этого водителя.

## Настройки

Все настройки из таблицы обязательны. Значения для запуска приведены в
[.env.example](.env.example), а `DATABASE_URL` создаётся в `.env` утилитой курса.
Остальные блоки `.env.example` относятся к следующим лабораторным.
Файлы `.env` и `.tripgo/` исключены из Git.

| Переменная | Значение в примере | Назначение |
|---|---|---|
| `HTTP_ADDR` | `:8080` | Адрес HTTP-сервера |
| `HTTP_READ_TIMEOUT` | `5s` | Время чтения запроса |
| `HTTP_READ_HEADER_TIMEOUT` | `2s` | Время чтения заголовков |
| `HTTP_WRITE_TIMEOUT` | `10s` | Время записи ответа |
| `HTTP_IDLE_TIMEOUT` | `60s` | Время ожидания следующего запроса в соединении |
| `LOG_LEVEL` | `info` | Уровень логирования |
| `SHUTDOWN_TIMEOUT` | `10s` | Общее время на остановку HTTP-сервера и пула БД |
| `DATABASE_URL` | Из `.env` | Строка подключения к PostgreSQL |
| `DATABASE_MAX_CONNS` | `10` | Максимальное число соединений с БД |
| `DATABASE_MIN_CONNS` | `2` | Минимальное число соединений с БД |
| `DATABASE_CONNECT_TIMEOUT` | `5s` | Время подключения и проверки БД при запуске |
| `DATABASE_QUERY_TIMEOUT` | `3s` | Время одного SQL-запроса |
| `DATABASE_TX_TIMEOUT` | `8s` | Время всей транзакции `Do`: от `BEGIN` до `COMMIT` |
| `DATABASE_MAX_CONN_LIFETIME` | `30m` | Время жизни соединения с БД |
| `IDEMPOTENCY_TTL` | `24h` | Срок действия ключа повторного запроса |
| `IDEMPOTENCY_CLEANUP_INTERVAL` | `1h` | Период удаления просроченных ключей |

Таймауты, интервалы и срок действия ключа должны быть положительными.
`DATABASE_TX_TIMEOUT` не может быть меньше `DATABASE_QUERY_TIMEOUT`.
`DATABASE_MAX_CONNS` должен быть больше нуля, `DATABASE_MIN_CONNS` — от нуля до максимума.

## Сборка и проверки

| Команда | Что делает |
|---|---|
| `make build` | Собирает программу в `bin/trip-service` |
| `make generate` | Генерирует HTTP-типы и маршруты по OpenAPI |
| `make test` | Запускает `go test -race ./...` |
| `make migrate` | Применяет ещё не выполненные миграции |
| `make migrate-status` | Показывает состояние миграций |
| `make migrate-down` | Откатывает последнюю миграцию |

Для проверки сборки и запуска команды тестирования:

```sh
make build
make test
```

В ЛР1 тестовых файлов нет, поэтому `make test` выводит `[no test files]`.
По разделу 6.4 задания тесты добавляются в ЛР2. Работа API проверяется запросами выше;
отсутствие ошибок у `make test` само по себе не проверяет поведение сервиса.

В проекте три миграции: поездки, история статусов и ключи идемпотентности.
`make migrate-down` удаляет таблицу последней миграции вместе с данными.
Для полного отката на отдельной проверочной БД команду выполняют трижды,
после чего `make migrate` создаёт таблицы заново.

Дополнительные сценарии проверки — в [разделе 7 задания](https://github.com/course-go-autumn-2026/course/blob/main/homework/tasks/01-http-and-postgres/README.md#7-как-проверить-себя):
одновременные запросы, откат при ошибке записи истории, потеря связи с БД и остановка сервиса.

## Решения

**Работа с БД.** Подключения переиспользуются через `pgxpool`. SQL строится
через `squirrel`, значения передаются параметрами `$1`, `$2` и далее.
Таблица `trips` хранит поездки, `trip_status_history` — изменения их статусов.
Структура таблиц задаётся миграциями по [схеме курса](contracts/schema.md).

**Транзакции.** `TxManager.Do` открывает транзакцию и передаёт её через контекст.
Репозиторий использует транзакцию из контекста, а вне `Do` — обычное соединение
из пула. При успехе выполняется `COMMIT`, при ошибке или панике — `ROLLBACK`.
Ошибка возвращается вызывающему коду, паника пробрасывается дальше.
Вложенный `Do` использует ту же транзакцию; ошибка внутри него не позволяет
подтвердить изменения, даже если внешний код её проигнорировал.
На всю транзакцию действует `DATABASE_TX_TIMEOUT`, на каждый запрос внутри неё —
`DATABASE_QUERY_TIMEOUT`, поэтому несколько запросов в транзакции не делят
бюджет одного запроса.
Создание или завершение поездки и запись её истории выполняются вместе:
при ошибке записи истории изменение поездки тоже откатывается.

**Уровень изоляции — Read Committed.** Для этой работы его достаточно:
создание защищено уникальным индексом, завершение — условием в `UPDATE`.
Команды внутри одной транзакции выполняются последовательно.

**Один водитель — одна активная поездка.** Уникальный индекс
`trips_driver_active_uidx` запрещает повторение `driver_id` среди строк со
статусом `active`, в том числе при одновременных запросах.
Нарушение этого индекса, код PostgreSQL `23505`, возвращается как `409 driver_busy`.

**Завершение поездки.** Обновление выполняется с условием
`WHERE id = ... AND status = 'active'`. Из двух одновременных запросов только
один завершит поездку, второй получит `409`. Если строка не обновлена,
дополнительное чтение отличает уже завершённую поездку от отсутствующей (`404`).

**Проверка состояния и остановка.** `/health` не обращается к БД.
`/ready` проверяет её доступность: возвращает `200 {"status":"ok"}` или
`503 {"status":"unavailable"}`. По `SIGINT` или `SIGTERM` сервис прекращает
принимать новые запросы, ждёт текущие, останавливает очистку ключей
идемпотентности и закрывает пул БД.
Если `SHUTDOWN_TIMEOUT` истёк, сервис пишет ошибку в лог и завершает работу принудительно.

## Дополнительное задание: идемпотентность

Клиент передаёт UUID в заголовке `Idempotency-Key`. Первый запрос создаёт поездку
и возвращает `201`, повтор с тем же ключом и данными возвращает первоначальный
ответ и `200`. Тот же ключ с другими данными даёт `409 idempotency_conflict`.
Без заголовка работает обычное создание поездки.

Для проверки завершите поездку из примера выше. В том же терминале, где задана
переменная `TRIP_DATA`, выполните следующую команду дважды:

```sh
curl -i -X POST http://localhost:8080/api/v1/trips \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: 7f1c2a54-6d0e-4a3b-9f21-0c8e5b3a77d1' \
  --data "$TRIP_DATA"
```

Ключ и первоначальная поездка хранятся в `trip_idempotency_keys` в одной
транзакции с созданием поездки и её истории. Это защищает от одновременных
повторов и сохраняет результат после перезапуска сервиса.
Сравниваются значения полей: пробелы и порядок полей в JSON значения не имеют.

Срок действия ключа задаётся `IDEMPOTENCY_TTL` — в примере 24 часа.
Повторы не продлевают срок. После истечения ключ можно использовать для новой
поездки; просроченная запись заменяется при успешном создании.

Просроченные ключи удаляет фоновая очистка: при запуске сервиса и затем каждые
`IDEMPOTENCY_CLEANUP_INTERVAL`. Записи удаляются пачками по 1000 отдельными
короткими запросами, поиск идёт по индексу `trip_idempotency_keys_expires_at_idx`.
Ключи, которые сейчас заняты запросом на создание, пропускаются (`SKIP LOCKED`),
поэтому очистка не ждёт таких запросов и не мешает им.
Повтор по действующему ключу возвращает первоначальное состояние поездки,
даже если она уже завершена. Текущее состояние можно получить через `GET`.

## Дополнительное задание: Docker

После запуска окружения курса и применения миграций на macOS с Docker Desktop:

```sh
make docker-build
make docker-run DOCKER_PORT=8081
```

В другом терминале:

```sh
curl -i http://localhost:8081/ready
```

Ожидается `200` и `{"status":"ok"}`. Внутри контейнера сервис слушает порт 8080,
а `DOCKER_PORT` задаёт порт на компьютере. Makefile берёт строку подключения
из `.env` и заменяет `localhost` или `127.0.0.1` на `host.docker.internal`.
Для остановки нажмите `Ctrl+C`; контейнер сервиса будет удалён автоматически.

Сборка в `deploy/Dockerfile` состоит из двух этапов: сначала компилируется
программа, затем только исполняемый файл копируется в образ на `scratch`.
Процесс работает от пользователя `65532:65532`, исходников и инструментов Go
в итоговом образе нет. Проверенный размер — **14,5 МБ** на `linux/arm64`.
Размер своей сборки можно посмотреть командой:

```sh
docker image ls tripgo:lab1 --format '{{.Size}}'
```
